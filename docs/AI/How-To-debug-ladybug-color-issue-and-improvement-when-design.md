# How-To：瓢蟲背色除錯，以及下次設計怎麼避開

日期：2026-10-22。這是工作筆記，不是 ADR。記錄 M5 瓢蟲從「俯視幾乎沒有紅」到「近看是猩紅黑點」這幾回的查法、誤判，以及生成網格時該先鎖住的東西。

## 結論

俯視呈青，是因為圓背的**著色法線朝下**。背面剔除留下的是外表面，正午的直接光打不上去，紅色 albedo 乘上一個接近 0 的漫反射，畫面上留下環境光，色相接近天際線的青。

當時 `critterTint` 的背已經是 `(1.0, 0.02, 0.02)`。再把紅調高不會出現。黑點只蓋住圓背頂部大約一成五，也不是背發青的原因。

修正在生成器：`tools/make_black_ant_glb.py` 的 `uv_sphere()` 讓三角形繞序和朝外的法線一致，`_face_outward()` 就不會把兩者一起翻轉。只重寫了 `koolApp/assets/models/insects/ladybug.glb`。粗糙度維持 `0.55`。

近景（暫停、運鏡關、縮放 6、三隻放在時鐘石外的空地）裡，背是猩紅、點是黑的。最密的一塊紅平均大約是 sRGB `(185, 18, 25)`。沒有發白，所以沒有再改色。

## 畫面上看到的是什麼

使用者的近圖是 `docs/screenshots/ladybug.png`（1603×928，選取中的瓢蟲，紫色檢視環）。殼上的像素偏藍，大約在 `(115–125, 140–152, 190–199)`，三通道比約 `1 : 1.21 : 1.63`。天際線調色盤是 `(0.45, 0.62, 0.85)`，比約 `1 : 1.38 : 1.89`。同一張圖的地面是暖土色，大約 `(161, 143, 129)`。地面是暖的，所以不是整個 framebuffer 把紅藍對調。

左側 3D 的昆蟲不上 glTF 材質。`parseGltfCritter` 只讀位置和法線。顏色是實例色：`deferredKslPbrShader` 把 `instanceColor` 寫進 g-buffer 當線性 albedo。圓背進 body 桶，名稱以 `Spot` 開頭的（七個點、`SpotHead`、`SpotPronotum`）進 mark 桶。一個網格一份顏色，所以紅殼和黑點必須分成兩份實例。Classic 2D 與方塊退路用 `WorldPalette` 的 `(0.8, 0.15, 0.15)`，不走 `critterTint`。調色盤紅不能拿來判斷 3D 背。

正午（`--shot=day` 把 `timeOfDay` 設成 0.45）太陽夠高，朝上的法線會被直接照亮。朝下的法線 `n·L` 被夾成 0，紅通道即使是 1 也乘不出紅。剩下的是環境項，看起來像天色。地面網格自己的法線朝上，所以土色仍暖。

## 法線為什麼會朝下

`uv_sphere()` 把頂點位置和儲存法線都設成單位球的朝外方向。頂點 `(0, 1, 0)` 的法線本來是 `(0, 1, 0)`。索引的繞序卻相反，第一個非退化三角形的幾何法線朝內。

`_face_outward()` 只看第一個非退化三角形。幾何法線和「朝外」點積為負時，呼叫 `Mesh.flipped()`：

- 交換三角形繞序，剔除所看到的正面變成朝外
- **同時把每條儲存法線取反**

剔除和光照用的不是同一個向量。翻完之後，光柵用的正面朝外，光照用的法線朝內。修正前的 `ladybug.glb` 上，冠頂位置 `(0, 1, 0)` 的儲存法線是 `(0, -1, 0)`，上半球法線平均大約 `(0, -0.76, 0)`，球上的三角形全部是幾何法線和儲存法線相反。

這個函式的名字像是在「讓面朝外」。它做的是把兩個「朝外」綁在一次翻轉裡。繞序錯、法線對的網格，會被修成繞序對、法線錯。沒有第二個斷言去檢查翻完之後的儲存法線。

修正後的繞序在呼叫 `_face_outward()` 之前就和朝外法線一致，函式直接把網格還回去，不再取反。冠頂法線是 `(0, 1, 0)`。`CritterGlbTest` 對解析後的 body（只有圓背）取最高頂點，要求法線 Y 大於 0.5。測試走 `parseGltfCritter`，所以包含節點變換裡的 inverse-transpose。正縮放不會把 +Y 再翻成 -Y。

`uv_sphere` 也負責螞蟻、道具、食物、三葉草和別的昆蟲上的球。改函式只影響**之後**再跑生成器的檔。已經寫進 repo 的 glb 維持原樣。這次只跑了 `python3 tools/make_outdoor_insects_glb.py ladybug`。沒有重寫甲蟲、獵物、捕食者、蜘蛛或螞蟻。`tapered_rod` 仍有一部分三角形和儲存法線不一致；瓢蟲的腳在近景裡是暗的，而且腳和螞蟻共用這支函式，所以沒有順手改。

位元組數和三角形數都不是新舊檔的證據。修正前後 `ladybug.glb` 都是 56988 bytes、2156 三角形。桌面從 `koolApp/assets` 載入。`desktopProcessResources` 顯示 UP-TO-DATE，不代表畫面上的是舊網格；js 的 processed 複本可以仍是舊檔、同樣的大小。

## 截圖為什麼會證明錯的事

### 量到的不是殼

`ec5cac8` 之前，有一張 `/tmp/ladybug-red-late.png` 在畫面邊緣裁到一塊偏紅，核心大約 `(165, 60, 54)`。那被寫成「背已經是猩紅」。使用者的選取近圖否定了這件事。邊緣的一塊顏色不能當成殼。

之後寫進 PLAN 或 CHANGELOG 的「俯視是猩紅」，必須是近景裡殼的像素，而且紅通道明顯高於綠和藍。

### 地圖中心不是空地

`SimConfig.clock.radius` 是 150。時鐘石在 `(width/2, height/2)`，預設 1400×840 就是 `(700, 420)`。3D 網格是一顆球，縮放 `(150, 36, 150×0.72)`，中心在當地地面高度再加 10。它在水平方向蓋過整個縮放 6 的視野。

1600×900、左側 74% 時，`fitScale` 約 0.85，縮放 6 大約 5 像素對 1 世界單位。半視野大約 117×89。時鐘石半徑 150 比這還大。昆蟲畫在 `GroundHeight` 上，石面在那附近高出地面幾十單位。放在中心 ±22 的瓢蟲在石頭裡面。

那張圖沒有亮紅像素。這只證明「畫面裡沒有殼」，不證明法線修正失敗。

### 運鏡在暫停時仍移動鏡頭

`AppSession.tick` 在 `paused` 時不推進模擬，但 `cinema` 預設是 true，仍呼叫 `CinemaDirector.update`。係數大約每幀 0.014，90 幀會把鏡頭拉向入口或廣角目標的一大段。`--shot=day` 本身不拉近，也不生瓢蟲。

瓢蟲要 `world.age > gracePeriod`（4000）且亂數低於 `ladybugSpawnRate`（0.0005）才生，上限是 2 再加上蟻數除以 40。第 90 幀仍在寬限期內。不手動放，日景截圖裡不會有瓢蟲。

驗證時暫時做過、**沒有進 commit** 的事：`paused = true`、`cinema = false`、`camera.zoom = 6`、鏡頭放在 `(220, 160)`，三隻在 `(200, 150)`、`(250, 175)`、`(180, 190)`。種子 12345 的八塊障礙石離這塊空地夠遠。提交前把 `AppSession.kt` 這段拿掉，再跑 Gradle。

### 第一張截圖的警告

kool 在第一次要求螢幕複本時會記 “First capture might be corrupted.” 第 90 幀就會觸發，把幀數往後挪不能避開。存下來的圖仍要打開看。那幾張是完整的遊戲畫面（暫停時蟻后年齡停在 0 分 0 秒），不是雜訊。沒有瓢蟲是構圖問題。

### 設定檔

截圖用 Gradle init script，只對 `runDesktop` 設 `-Duser.home` 到暫存目錄。看 `$HOME/.myants/antsim.ui.v1.txt` 的 mtime。這幾次前後都是 `1792678166`（2026-10-22 22:09:26）。不要為了「還原」去改那個檔。

## 除錯方式要改成這樣

依序問，某一層已經對了就停，不要在那一層再加料。

1. **像素是不是殼。** 先確認選取環或近景裡有那隻蟲。量殼的範圍，不量畫面邊緣的色塊。0 個亮紅像素時，先問蟲在不在畫面裡。
2. **是不是整張圖的通道錯了。** 看地面或三葉草。土色仍暖，就不是紅藍對調。
3. **albedo 是不是已經是目標色。** 讀 `critterTint`。背已經是 `(1, 0.02, 0.02)` 時，不要再加紅。
4. **載入的網格法線朝哪。** 解析遊戲真正讀的 glb，看冠頂（最高頂點）的法線 Y。三角形數和檔案大小不算。也要比幾何法線和儲存法線是不是同一側。
5. **截圖裡有沒有這隻蟲。** 離開時鐘石，關掉運鏡，暫停，手動放在空地上再拉近。種子 12345 的障礙石位置可以用和 `Rng` 相同的 mulberry32 先算出來，不要把蟲放進半徑 20–50 的石頭。
6. **這時才決定要不要改色。** 近景的殼若發粉或發白，只改瓢蟲 body 那一個 `Color` 和 `CritterTintTest`，再拍一次。殼仍是青，就回到第 4 步，不要加紅。

量色用門檻，不用「看起來有點紅」：在左側 74% 裡找 `r` 明顯大於 `g` 和 `b` 的像素（這次用 `r > 160` 且比另外兩通道至少高 40），再取最密的一塊求平均。這次最密一塊約 348 像素，平均 `(185, 18, 25)`。單點最紅 `(181, 5, 7)` 只作參考，平均才代表殼。

看圖的描述可以確認有沒有黑點、頭是不是黑的。顏色以像素統計為準。描述說「沒有瓢蟲」時，再對一下亮紅像素是不是 0，避免把石頭上的土色當成殼。

成功之後才寫「俯視是猩紅」。寫早了會讓下一回把錯誤的截圖當成基線。

暫時擺蟲的程式在測試和 commit 之前刪掉。Gradle 門檻是：

```text
./gradlew compileKotlinDesktop compileKotlinJs desktopTest
```

文件若要寫新 commit 的 SHA，分兩個 commit：先程式（含 CHANGELOG、PLAN 的內容句、deviations），再一個只改 PLAN SHA 列的 commit。

## 下次設計圓背、上色、截圖時

### 生成網格

一顆要被光照的球，同時有兩件事要對：

- 三角形繞序，決定背面剔除留下哪一面
- 儲存法線，決定 Lambert 和環境光用哪個方向

兩件要一起朝外。不要只修其中一件。`_face_outward` 這種「繞序錯了就把法線也反過來」的修法，會把另一件修壞，而且從外面看不出來：面還在，只是不受光。

生成時對**每一個**三角形檢查，不要只看第一個：

- 幾何法線和三角形中心的朝外方向點積為正
- 三個頂點的儲存法線平均，和幾何法線點積為正
- 冠頂（最大 Y）的儲存法線 Y 大於 0.5

檢查失敗就停，不要靜默翻轉。靜默翻轉是這次 bug 能進 repo 的原因。

Kotlin 測試鎖的是遊戲載入後的結果，不只是 Python 裡的陣列。`CritterGlbTest.assertLadybugDome` 的冠頂斷言就是這個。新的圓形部件要有同樣的一行。只鎖長度、頭在 +X、三角形數 700–2200、節點名字，鎖不住光照。

`tapered_rod` 還沒做這個檢查。要改之前先看近景裡的腳。它和螞蟻共用，不能為了瓢蟲重生成全部腳。

### 上色

無貼圖的 PBR 昆蟲，顏色在 `critterTint`，不在 glb 材質。把 glb 的 baseColor 塗紅不會出現在畫面上。

一個實例一份 albedo。紅背和黑點必須是不同網格。黑點、黑頭、黑前胸靠名稱進 mark 桶（`Spot`、鞘翅）。不要為了瓢蟲加一條「所有 Head 都算 mark」的全域規則，那會改到別的昆蟲。

調色盤 `(0.8, 0.15, 0.15)` 在正午會被打成偏粉。3D 背用更純的紅，是為了光照之後仍像照片的猩紅。Classic 2D 留在調色盤。兩套顏色都要在測試裡各鎖一次，並且註明哪一套是給哪一個渲染器用的。

改色的順序：法線朝外，拍到殼，殼發粉或發白，才動那一個 `Color` 和對應測試。粗糙度 `0.55` 這次夠用。發白再考慮只降這一隻的粗糙度，不要連別的昆蟲一起降。

### 截圖

日景預設鏡頭在地圖中心，那裡是時鐘石。縮放 6 的視野整個落在石頭的水平範圍裡。這個鏡頭不能用來驗昆蟲顏色。

要驗某一隻蟲：

- 暫存 `user.home`，結束後對一下真實設定檔的 mtime
- `--seed=12345 --quality=medium --renderer=3d`
- 暫停，並把 `cinema` 關掉
- 鏡頭與蟲都放在時鐘石（半徑 150）和障礙石之外，仍落在縮放 6 的視野裡
- 用程式自己的 framebuffer PNG。macOS `screencapture` 抓不到這個視窗
- 圖出現後關掉 Gradle，不要留著視窗
- “First capture might be corrupted” 之後仍要看圖
- 不點 HUD、Inspect、Classic 2D，除非那次改的就是它們
- 不把畫面上的 FPS 寫進結論

蟲會走。速度 1 的瓢蟲在拉近的視野裡，幾十幀就走出畫面。暫停是為了讓牠留在鏡頭下，不是為了改模擬。這段程式不要進 commit，也不要改 `ladybugSpawnRate` 或 `gracePeriod`。

### 共用生成器

`uv_sphere` 的修正不會自動更新舊 glb。文件要寫明重跑了哪一個檔。沒有點名的生物維持原檔。

若以後某個球體部件看起來像天色，先量那顆球的冠頂法線，再決定要不要重生成。不要先改色。重生成時只寫那個檔，並重跑它的 glb 測試。甲蟲的 glb 由 Blender 寫，不要用這支 Python 蓋掉。

三角形數相同、檔案大小相同，都可能是新網格。以冠頂法線或檔案雜湊為準。

### 什麼算做完

三件一起成立才寫「背是猩紅」：

1. 解析後的冠頂法線 Y 大於 0.5，測試綠
2. 近景裡看得到殼，黑點仍暗，頭和前胸仍黑
3. 殼上最密的紅塊，紅通道明顯高於綠和藍，而且沒有整片發白

缺第 2 件時，第 1 件只證明檔案對了，不證明玩家看得到。缺第 1 件時，第 3 件可能又是在量別的像素。
